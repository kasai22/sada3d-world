# Reality 3D — Catalog approval process

How a business decision becomes a launchable product. This document describes the **process**. The current **state** lives in generated documents and in the CMS, and nowhere else:

| Where | What it holds | Source of truth |
|---|---|---|
| [`MANUFACTURING_CAPABILITY.md`](MANUFACTURING_CAPABILITY.md) | Processes, printer, material matrix, limitations, the business decision ledger — each KNOWN / PROPOSED / MISSING / APPROVED / BLOCKED | `src/content/catalog/decisions/business-decisions.json` + `src/content/catalog/manufacturing.ts` |
| [`LAUNCH_CATALOG.md`](LAUNCH_CATALOG.md) | Catalog size vs target, the business input matrix, the seed products field by field, why each cannot launch, services, policies | `src/content/catalog/` + `lib/catalog/launch.ts` |
| Payload admin → Products → **Launch status** tab | Every product in the CMS, seed and administrator-managed, with every blocking reason | The product record + price approvals + the ledger |
| `npm run content:verify` | Seed parity, readiness of every CMS product, missing media files | The database |

The two documents are generated by `npm run content:docs`. `npm test` fails if either differs from the code.

**ENGINEERING COMPLETE ≠ BUSINESS APPROVED ≠ LAUNCH READY.** As of Stage 20 the admin can create, define, approve and publish products and categories without a deployment. As of Stage 19.8, manufacturing processes, materials, colours, layer heights, build volume and catalog policy are business-approved. No product, price, SKU or image is approved, so the catalog is not launch-ready.

**COMING SOON ≠ APPROVED.** Stage 19.9 shows planned capabilities (ABS, Resin, SLA, Smoothed, Matte) to customers as Coming Soon. None of them is approved, and none can be quoted, carted, ordered or used by a publishable product.

## The chain

```text
Business decision                     reference + approver + date — never inferred
        ↓
  ┌─────────────────────────────────────────────┬──────────────────────────────────────────┐
  │ Capability & policy                         │ Products                                 │
  │ business-decisions.json                     │ Payload admin (administrator-managed)    │
  │ (npm run content:decisions)                 │ or the repository seed (p-101 – p-103)   │
  └─────────────────────────────────────────────┴──────────────────────────────────────────┘
        ↓
Configurator, quote engine, storefront filters, admin validators   (read the ledger)
        ↓
Launch assessment                     technical + approval + price + media + manufacturing + commercial
        ↓
content:verify / --require-launch     release gate
        ↓
Storefront                            launch mode: launch-approved products and approved prices only
```

## Capability status: Available, Coming soon, Unavailable

Every manufacturing process, material, finish and colour has exactly one capability status, derived in `src/content/catalog/capabilities.ts` and read by the configurator, quote engine, cart, checkout, admin, materials pages, `content:verify` and the generated documents.

| Status | Means | Comes from | Customers see | Quote / cart / checkout / order | Product using it |
|---|---|---|---|---|---|
| **AVAILABLE** | Approved production capability | An APPROVED record in the business decision ledger — reference, approver, date | An active option | Accepted | Can be published and launched (if every other gate passes) |
| **COMING SOON** | Planned, **not approved** | An entry in `src/content/catalog/roadmap.json` — a reference only: no approver, no date, no specification | A muted, badged, disabled option; a message such as "ABS printing is coming soon to Reality 3D." | **Refused** (HTTP 400, "Capability currently unavailable — …") | Can be drafted in the admin; cannot be published, approved or launched |
| **UNAVAILABLE** | Not approved and not planned | Neither | Nothing | Refused | Cannot be saved |

Rules:
- The ledger is read first. A roadmap entry is consulted only after the ledger has said no, so the roadmap can never make anything available.
- A roadmap entry states only `kind`, `value` and `reference`. A date, timeline, machine, layer height or tolerance is rejected by validation, and `content:verify` counts an invalid entry as blocking.
- Coming Soon capabilities are never counted as approved manufacturing capability: the Manufacturing line of `content:verify`, the launch gate and the generated documents read approvals only.
- To make a Coming Soon capability available: record an APPROVED ledger decision (`npm run content:decisions`), with any values it needs. For Smoothed or Matte, that is a `finish` decision. Then regenerate the documents and rebuild.
- Capability status is not product approval, price approval, Payload publication or technical validity. Those remain separate questions about each product.

Now: available — FDM; PLA, PETG, TPU; Black, White; FDM layer heights 0.20 / 0.16 / 0.12 mm; Standard finish; 256 × 256 × 256 mm build volume. Coming soon — SLA; ABS, Resin; Smoothed, Matte.

## Statuses

**Stated facts.** Every manufacturing and commercial input is one of:
- **KNOWN** — verified from the repository, or a manufacturer specification Reality 3D supplied as the technical reference. A specification is not a production guarantee.
- **PROPOSED** — entered or described, not signed off. A value typed into the admin is PROPOSED until a complete approval record covers it.
- **MISSING** — no value. None is invented.
- **APPROVED** — with a reference, an approver and a date.
- **BLOCKED** — decided against (for example ABS, resin, SLA), with the decision cited.

A partial approval record (a reference without an approver, a date in the wrong format) approves nothing.

**Product approval status.** draft → proposed → provisional → approved; archived withdraws a product. Separate from Payload publication (draft / published). Draft and archived products cannot be published.

**Product ownership (`source`).**
- **Administrator-managed** — created or saved by an operator in the admin. The business's own record. `content:import` never writes, unpublishes or deletes it.
- **Repository seed** — p-101, p-102 and p-103, written by `content:import`. The moment an operator saves one, it becomes administrator-managed and the import stops syncing it.

**Launch status (computed).** A product is launch-ready only when every item holds; each unmet item is reported as its own reason:
- technically valid (identity, category, model, specifications, copy claims)
- product approved, with an approval record
- price approved (a price approval in effect whose amount equals the price) or quote-only
- media approved: a photo or render under `/catalog/<slug>/`, classified, matching the visual requirement, with a media approval record, and the file present
- the product's material on its process is approved capability, and the launch-required manufacturing limitations are approved
- SKU, product class, pricing model, customer, use case, copy and visual requirement covered by a complete commercial approval
- every open business question answered YES with a reference (a NO blocks)

**Catalog launch** additionally requires the launch-target number of launch-ready products. The target is 12 and is **PROPOSED**: launching with fewer is possible only by recording an explicit `launch-target` decision.

## A. Record business and manufacturing decisions

Decisions are data in `src/content/catalog/decisions/business-decisions.json`: an append-only ledger. Every record has an id (`BD-YYYY-MM-DD-NN`), a kind, a subject, `APPROVED` or `NOT_APPROVED`, optional values, and `{ reference, approvedBy, approvedOn }`.

| Kind | Subject | Values |
|---|---|---|
| `manufacturing-platform` | `fdm` | `printer`, `buildVolumeMm {x,y,z}`, `specificationReference`, optional nozzle and hotend data |
| `manufacturing-process` | `fdm`, `sla` | — |
| `material` | `pla`, `petg`, `tpu`, `abs`, `resin` | — |
| `finish` | `standard`, `smooth`, `matte` | — (Stage 19.9: none approved; Standard is the process output) |
| `material-colours` | any label | `materials`, `colours` (from the colour vocabulary only) |
| `layer-heights` | `fdm` | `layerHeights` |
| `manufacturing-limitation` | a documented topic, e.g. `Minimum wall thickness` | `policy` (required when approved) |
| `launch-target` | `catalog` | `minimumLaunchReadyProducts` |
| `catalog-policy` | `catalog-strategy`, `sales-claims`, `initial-products` | — |

To add decisions in bulk:

```bash
npm run content:decisions                                   # validate the committed ledger
npm run content:decisions -- --input decisions.json         # dry run: accepted / duplicate / rejected, with reasons
npm run content:decisions -- --input decisions.json --report result.json
npm run content:decisions -- --input decisions.json --apply # append — only if nothing is rejected
npm run content:docs && npm test && npm run build
```

Rules the intake enforces:
- A malformed record is rejected with every reason; nothing is repaired or defaulted.
- A record identical to one in the ledger is a duplicate and skipped, so re-applying a file changes nothing.
- A record reusing an id with different content is rejected. To change a decision, add a new record with a later date; the latest valid record is in effect and the old one stays in the audit trail.
- A record that conflicts with another on the same date is rejected. (In a hand-edited ledger both would be withheld.)
- One rejection and the whole batch is not applied. `--dry-run` always wins over `--apply`.

What the ledger controls: materials, colours and layer heights offered in the configurator and quote engine; storefront material/technology/colour filters; the admin's technology, material, colour and layer-height validators; the FDM build-volume check on uploaded models; manufacturing approval in launch readiness.

**Still missing, and blocking manufacturing sign-off:** minimum wall thickness, minimum feature size, dimensional accuracy. Also missing: production tolerance, inspection criteria, lead time. Each stays `MISSING — REQUIRES Reality 3D MANUFACTURING VALIDATION` until a `manufacturing-limitation` decision with a policy is recorded. None is derived from the printer specification.

## B. Add a product (Payload admin) — no deployment

The admin is the product entry point. A normal catalog product is added, defined, priced, approved and published entirely in Payload; nothing in the repository changes. (Image and model **files** still arrive under `public/` with a deployment until Payload Media has a storage adapter — the product **record** does not.)

```text
Create product → add image → add 3D model → define manufacturing → define commercial information
→ set SKU → set price → submit for approval (Proposed) → READY FOR REVIEW → approve → publish
```

**Products → Create new.** It starts as a **draft**; the product id (`p-NNN`) is assigned automatically and is never a retired id. Tabs, in order:

1. **Launch status** — the readiness panel (below). Read-only, computed on every read.
2. **Basic information** — name, slug, summary, description, SKU.
3. **Category** — leaf category and its browse (top-level) category.
4. **Application** — target customers, use case, applications.
5. **Manufacturing** — technology, labelled with its status (FDM — Available now; SLA — Coming soon; SLS — Not available); quality options (approved FDM layer heights only: 0.20 / 0.16 / 0.12 MM).
6. **Material** — PLA, PETG, TPU available now; ABS and Resin selectable only for a draft future product.
7. **Colours** — approved colours only: Black, White.
8. **Dimensions** — only measured or approved values (dimensions, bore diameter, tooth count, part count as specification rows; weight). Every field is optional: an empty table beats an invented one.
9. **Pricing** — price, price status, currency (INR), pricing model, product class, availability.
10. **Media** — Visual: source under `/catalog/<slug>/`, alt text, type (Photograph / Approved render), media approval; visual requirement; render specification.
11. **3D model** — a model file under `/models/` (STL, OBJ, GLB), verified on the server.
12. **SEO** — optional title and description (search results usually show about 60 and 160 characters); product facts only — a claim here blocks launch like a claim in the copy.
13. **Approval** — approval status, product approval record, commercial approval record, open business questions.
14. **Featured** — Featured and Recommended (editorial), badge.

Typed values are PROPOSED. Nothing in the admin becomes approved because it has a value.

### Product class requirements

| Requirement | Standard | Configurable | Quote-only |
|---|---|---|---|
| Name, slug, category, description | Yes | Yes | Yes |
| Target customer and use case | Yes | Yes | Yes |
| Technology and material (available capability) | Yes | Yes | Yes |
| SKU | Yes | Yes | No |
| Pricing | Approved price | Approved pricing mechanism (not yet possible: the quote engine rules are provisional) | No fixed price |
| Configuration (at least two material, colour or quality choices) | No | Yes | No |
| Approved media | Yes | Yes | Yes |
| Commercial approval and product approval | Yes | Yes | Yes |

Custom manufacturing from the customer's own model is a service (`/custom-print`), never a catalog product class.

### SKU

Entered by the business, never generated. 3–32 characters: uppercase letters and digits in hyphen-joined groups (example shape `RG-GEAR-024`; the scheme is the business's choice). Unique — the admin refuses a duplicate on save. A malformed SKU is refused on save and blocks launch.

### Launch status and launch stage

The **Launch status** tab is the canonical readiness view. It shows the **Launch stage** and a panel:

```text
TECHNICAL          ✓ Valid
MANUFACTURING      ✓ FDM / PLA approved        (or ✕ with the reason)
COMMERCIAL         ✕ Missing SKU               → Basic information (SKU), Application and Pricing tabs, then Approval → Commercial approval
PRICE              ✕ Missing approved price    → Pricing tab, and Catalog › Price approvals
MEDIA              ✕ Missing approved image    → Media tab → Visual, then its media approval
PRODUCT APPROVAL   ✕ Product not approved      → Approval tab
PUBLICATION        ✕ Not published             → Publish
FINAL              NOT READY
```

Stages are derived, never selected: **NOT READY** (a prerequisite fails) → **READY FOR REVIEW** (everything passes; approve it) → **APPROVED** (publish it) → **LAUNCH READY** (approved and published). The pointers name admin tabs and collections; they are not links, because an edit-view tab has no URL.

### Product list

Columns: product, SKU, category, material, class, price, media status, approval, launch stage, readiness summary (`TECH ✓ · MFG ✕ · COMM ✕ · PRICE ✕ · MEDIA ✕ · APPROVAL ✕`), featured, updated. Search by name, SKU, slug or product id; filter by category, material, class, approval status or price status. Launch stage is computed live from the record, price approvals and the capability ledger, so it is shown rather than stored — and therefore is not a database filter.

### Bulk operations

Allowed: category, featured, recommended, badge, publish and unpublish (withdrawal). Not bulk-editable: approval status, the product approval record, commercial approval, media approval, price, price status, SKU, slug, product id, open questions. There is no "Approve all": every approval is individual, guarded and recorded.

### Categories (Catalog › Categories)

An administrator adds a category in the admin: a lowercase, hyphenated identifier, a name, a description, and either a parent or "Top-level browse destination". Once published it appears in filters, breadcrumbs and labels and — when it has a launch-visible product — in the shop rail, footer, homepage index, sitemap and its own `/shop/<category>` page, without a deployment. Refused: an invalid identifier; a top-level category that is not a browse destination (or a child that is one); a cycle; changing the identifier, unpublishing, or deleting while products or sub-categories use it. The import never overwrites or withdraws an administrator's category.

## C. Approve a product

1. **Commercial decisions.** Fill SKU, class, pricing model, customers, use case and visual requirement; then complete the **Commercial approval** record (reference; approver and date are stamped from the operator and today when left empty). An approval does not fill a missing value.
2. **Price.** Under **Catalog › Price approvals**, add a record (whole rupees, INR, effective date, reference, approver). Records cannot be edited or deleted; a new price needs a new record. Then set the product price to that amount and price status **Approved**. The CMS refuses an approved price with no matching approval in effect, and the storefront re-checks on every read. An older approval never authorises a newer price. A quote-only product has price 0 and needs no price approval. The seed products' ₹650, ₹2,650 and ₹730 are provisional engine output until approved this way.
3. **Media.** Commit the real photograph or approved render under `public/catalog/<slug>/`. Set the source, alt and type, and complete the media approval record. Media status reads MISSING → PROPOSED → APPROVED. Placeholder or stock names, files filed under another product, missing files and unclassified images are refused.
4. **3D model.** Commit the model under `public/models/` and set its path and format. It must verify (closed mesh or valid glTF, within the build volume) or the product is technically blocked.
5. **Open questions.** Answer each YES or NO with a reference. Unanswered blocks; NO blocks.
6. **Submit.** Set approval status **Proposed**. When the Launch status reads **READY FOR REVIEW**, set **Approved** with the product approval reference. The save is refused and rolled back — with every remaining reason listed — unless every prerequisite holds. There is no override.
7. **Publish.** The stage becomes **LAUNCH READY**; the product appears in launch mode.
8. **Featured / Recommended (optional).** Editorial choices. Featured is honoured only for launch-ready products; Recommended labels a product wherever it is shown. No sales-ranking label ("Best seller", "Most popular", "#1") can be entered.

The seed products follow the same rules through `src/content/catalog` and `content:import`, which writes approval as a second step so the same guard applies.

## D. Verify and release

```bash
npm run content:docs
npm run content:import                        # a second run must report everything unchanged
npm run content:verify                        # parity (seed), readiness (all CMS products), media files
npm run content:verify -- --require-launch    # release gate: exits non-zero until launch-ready
```

`content:import` never touches customers, accounts, orders, carts, payments, manufacturing jobs, designs or uploaded files, and never overwrites an administrator-managed product.

## Refused saves (CMS)

- publishing a draft or archived product
- publishing a product whose process or material is Coming Soon ("… can be kept as a draft, but it cannot be published until … is approved")
- an unavailable (neither approved nor planned) technology or material, even in a draft
- an unapproved colour or layer height
- approving a product without a reference, or while any launch prerequisite is unmet
- a commercial, media or answer approval started without a reference
- approving media with no source or no photo/render classification
- an approved price without a matching price approval in effect
- a quote-only price that is not 0, or a price of 0 that is not quote-only
- a malformed or duplicate SKU
- a badge claiming a sales ranking
- a model path outside /models/
- a category change that would orphan products (see Categories)

## Known constraints

- **One operator role.** Reviewer and approver cannot be separated in the CMS. Each approval record names the person responsible.
- **No media storage adapter.** Approved images are committed under `public/catalog/` until one is attached.
- **Custom-print pricing is provisional.** The quote engine rules (`demo-2026-01`) are not approved commercial pricing and are never promoted to an approved price. Payment integration is Stage 20 and has not begun.
- **Ledger changes need a build.** The storefront, configurator and quote engine read the ledger at build time.
